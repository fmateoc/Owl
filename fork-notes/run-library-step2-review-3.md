| H1 | medium-high | **The worker's date freeze does not reach the `withSSAges` candidates, so the freeze is wrong for any preset that searches claiming ages.** `Worker._solve` freezes with `with asof.as_of(as_of_date):` (`worker.py:171`), which is **thread-local** since F5. `Plan._ssAgeSearch` runs every candidate on a `ThreadPoolExecutor` thread (`plan.py:7034-7067`). In such a thread, `asof.today()` finds no thread-local value and falls back to the process-wide `_AS_OF`, which is None in a worker. Each candidate's `setSocialSecurity` (`thisyear = asof.today().year`) therefore builds its SS streams for the **real** year, while the plan's `year_n` starts in the run's plan year. Today the only exposed preset is `custom` on a case with `withSSAges` (the template has `withSSAges = "optimize"`); step 6's two Ages presets are built on this path. It also breaks section 5's promise that `owlcli run --as-of` reproduces a run: the CLI freezes process-wide (`set_as_of`), so its candidates see the frozen date and the worker's do not. The F5 test `test_the_context_freeze_does_not_leak_across_threads` asserts exactly the behaviour that causes this. Fix: a worker is one job per process, so it should freeze process-wide (`asof.set_as_of(as_of_date)` at the start of `_solve`). The thread-local context stays for the interface's captures. Add a worker test that runs a `withSSAges` solve with the session pin cleared (H2). | Probe `probe_threads.py`: inside `asof.as_of("2025-03-01")`, the main thread reads 2025-03-01 and a pool thread reads 2026-11-02. On `Case_jack+jill` with `withSSAges="optimize"` and `maxIter=3`, `setSocialSecurity` was called **378 times on `ssages` threads with year 2026** and 2 times on the main thread with 2025. Probe `probe_threads2.py`: the same solve gives different results under the two freezes. Context (the worker's way): ages 68y11m / 65y11m, objective \$106,737.07. | H3 | medium | **For one hour every November, live workers are marked dead (DST fall-back).** `now_iso()` writes naive local time (`results.py:76`). `heartbeat_age()` reads it back with `datetime.fromisoformat(beat).timestamp()` (`results.py:402`), and for an ambiguous local time that resolves to the *first* occurrence (fold=0). Every heartbeat written in the repeated hour is therefore read as one hour old. `adopt()` (`jobs.py:147`) runs every two seconds while a Queue page is open, marks the live worker interrupted ("the worker's heartbeat stopped"), and the worker then stops at its next check. The household is in America/New_York. The same naive stamps drive `queued` (the dispatch order and the folder names) and the Queue page's elapsed column, which are wrong in that hour, but harmlessly so. Fix: write heartbeats as epoch seconds or as UTC-aware ISO strings (`datetime.now(timezone.utc)`), and parse them aware. | `TZ=America/New_York`. A heartbeat written at 06:30 UTC (01:30 EST, the second pass) is stamped `2026-11-01T01:30:00`. `JobRecord.heartbeat_age(now=<5 s later>)` returns **3605.0**, which fails `< HEARTBEAT_MAX_AGE` (120 s). The same stamp written at 05:30 UTC (01:30 EDT) reads 0 s. Checked at the function level; no manager was run across a real DST change. |
| H4 | low-medium | **F2's guard on `record.json` is check-then-write outside the job lock, so a stale worker can still leave its record in a folder that "run again" has cleaned.** `_write_record` calls `self.job.is_mine(token)` (`worker.py:258`), then `build_record` (whose `engine_provenance()` runs three `git` subprocesses), then `write_record` (`worker.py:280`), and none of this holds `status.lock`. This is S8's own sleep scenario, the class G2 closed for the artifacts but not for the record. It is also the opposite of F6's intent: the old record should have become `record.prev.json`. If the new attempt is then force-cancelled (the Queue's only cancel, N1), it writes no record, so the stale "solved" record stays. Simplest: build the record first, then write it through a `JobRecord.publish_record(token, doc)`. | Probe (a pytest file run once, then deleted): `build_record` held for the "solved" call, then the job marked interrupted, `requeue()`, release. | H5 | low-medium | **The queue moves only while a Queue page is open.** `JobManager.tick()` (dispatch, adoption, interruption) has three callers: `enqueue`, `run_again` and the Queue page's fragment (`ui/Queue.py:75`); checked with grep. The job is not lost (S2 holds, as the check says), but section 8.2 calls the manager "one per server", and the page's own caption says closing the tab does not stop jobs. That is true of running jobs and not of waiting ones. It matters most for step 6's "run the whole collection again" batch. Not run in a browser. |
| H6 | low | **`plan.pkl` staleness ignores the Owl commit, and a failed unpickle is not soft.** Section 5 says that the cache is "valid only for the environment in record.json (commit, Python and package versions, S6)". `load_plan` compares only `record["environment"]` (`results.py:526`), and `environment()` holds Python and package versions; the commit is in `record["engine"]` and is never compared. Also, `pickle.loads` (`results.py:529`) is not wrapped, so a pickle that fails to load (a module renamed) raises instead of returning None, against the docstring's "fails soft". ## Minors (fixed on 2026-11-02, the user's call; see the dispositions)

| # | Finding |
|---|---|
| N1 | The Queue's Cancel button always calls `manager.cancel(job, force=True)` (`Queue.py:106`). Wherever the start token can be read (Linux, Windows), the worker is killed at once, so a cancel from the interface never takes the cooperative path. In that case the worker writes no "interrupted" `record.json` (F6's point, S3) and leaves its staging folder behind. A two-stage button (cooperative cancel first, "kill" offered once the heartbeat shows it still running after a few seconds) would keep both. |
| N2 | The page caption says "Elapsed is measured from queue time", but the column measures from `started` once the job has started (`started or queued`). |
| N3 | `JobRecord.update` falls back to the in-memory `self.doc` when the on-disk read fails under the lock (`results.py:250-251`), checks the token against that in-memory copy and then writes it back. A failed read can therefore revert a cancel flag or a re-queue's new token on disk. This is inferred: a read failure under the lock needs an unlocked writer or an OS error, and no probe was run. Raising, or skipping the write, would be safer than writing a stale document. |
| N4 | On Windows, `requeue` unlinks `Results.xlsx` under the lock. If the user has the workbook open in Excel, the unlink fails (Windows file-sharing behaviour, recalled, not run) after `summary.json` and `plan.json` are already gone, and the exception reaches the button. The folder is then half-cleaned, with `record.json` not yet moved. Moving the old artifacts aside (or into an `attempt-<n>` folder) before deleting anything would keep `requeue` all-or-nothing. |
| N5 | `quick` forces only `withSSAges = "fixed"`. On the template (`withMedicare = "optimize"`), every loop iteration is still a branch-and-bound MIP, and a case that names `mipStrategy = "local-search"` runs local search. Section 8.1 calls quick "the default loop". If the case's own modes are what is meant, the preset's help text should say so; if the loop is what is meant, quick should also force the loop modes. (The synthetic baseline's quick solve took 11.4 s in the step's own check, so this is wording or intent, not cost.) |
