# Phase 0: first scenarios with `owlcli run` and `owlcli compare`

These runs are made **offline, by the user**, on the real case in `otherFiles/` (CLAUDE.md,
"Household data"). The whole set below except the work sweep also runs in one command,
`fork-notes/synthetic/run_suite.py` (one report, feature checks); cloud sessions run it on the
synthetic household of `fork-notes/synthetic/` to check that every scenario solves and reads well.

## Where the files live

| File | In the repo (templates, no personal data) | Filled-in copy (private) |
|---|---|---|
| Case file | `fork-notes/phase0/Case_us.template.toml` | `otherFiles/Case_us.toml` |
| HFP workbook | generated by `fork-notes/phase0/gen_hfp_us.py` | `otherFiles/HFP_us.xlsx`, `otherFiles/HFP_us_2027.xlsx` |

`otherFiles/` is gitignored by upstream itself. The fork is public, so real balances, PIAs and
wages go only there. Set up once:

```bash
mkdir -p otherFiles
cp fork-notes/phase0/Case_us.template.toml otherFiles/Case_us.toml
uv run python fork-notes/phase0/gen_hfp_us.py                             # HFP_us.xlsx
uv run python fork-notes/phase0/gen_hfp_us.py otherFiles/HFP_us_2027.xlsx  # work one more year
```

Then fill in the TODOs. The HFP path in the case file is resolved relative to the case file, so
both workbooks sit next to it. Save the TOML as UTF-8: a Windows-1252 file (an em dash from Word
or Notepad, byte 0x97) stops `owlcli` with a `UnicodeDecodeError` before it reads anything.

**Reproducibility:** `rates_selection.method = "conservative"` is deterministic. For `historical` or
a stochastic method, pin the window or `--seed` and record it with each output.

## Baseline

```bash
owlcli run otherFiles/Case_us.toml
```

Spending comes from the HFP Budget sheet (`spending_profile = "budget"` since 2026-10-27; section 5
for the line format). `gen_hfp_us.py` writes a discretionary `core` line and the two essential
gold-plan lines. Under the template's `maxSpending`, `core` only sets the shape: the solver scales
it (the Summary's *Discretionary spending (share of budget)*), so its amount does not change the
plan; the gold lines are paid at their amounts. With `core` alone the plan is the old `flat` one
(checked on a stand-in: the same net spending in every year). Under `maxBequest` or with
`netSpending`, enter the real `core` amount.

`owlcli compare` always runs the case as the base and one variant defined by `--set`; at least one
`--set` is required. Each block below is one comparison against the baseline.

## 1. Retire year (end of 2026 vs end of 2027)

```bash
owlcli compare otherFiles/Case_us.toml \
  --set household_financial_profile.HFP_file_name=HFP_us_2027.xlsx
```

If the extra year changes employer health coverage, also move `aca_settings.aca_start_year` to 2028
in the same comparison.

## 2. Social Security claiming (baseline co-optimizes the ages)

```bash
for ages in "[62.0, 62.0]" "[67.0, 67.0]" "[70.0, 70.0]"; do
  owlcli compare otherFiles/Case_us.toml \
    --set solver_options.withSSAges=fixed \
    --set "fixed_income.social_security_ages=$ages"
done
```

## 3. Residency (baseline: NY outside Yonkers/NYC, i.e. rest of Westchester)

```bash
owlcli compare otherFiles/Case_us.toml --set basic_info.locality=Yonkers
owlcli compare otherFiles/Case_us.toml --set basic_info.locality=NYC
# A later move within NY, e.g. from Yonkers to another Westchester district in 2032:
owlcli compare otherFiles/Case_us.toml --set 'basic_info.moves=[{"year": 2032, "state": "NY", "locality": "", "school_district": "City of Rye / Rye"}]'
```

**NJ is out of the investigation (2026-10-17).** The household does not expect to live there, and
the fork's NJ rules (retirement exclusion, line 41, line 31) were removed the same day: an NJ case
runs on upstream's NJ, which overstates NJ tax for retirees, so NJ variants are not run.

NY benefit recapture (above $107,650 of NY AGI) applies automatically, and the Yonkers surcharge
includes it. Phase 3 added NY's own itemized deduction (IT-196: property tax uncapped, mortgage
interest, charity, medical above 10% of AGI) under `withItemized` (default `"loop"`), with the
federal itemized deduction. On the synthetic couple NY itemizing was worth $27-39k of bequest exact
and $6-11k under local search at $20-25k of property tax (`fork-notes/phase3-review.md`, A.2). To
see what the deductions are worth for us, switch them off in the variant only:

```bash
owlcli compare otherFiles/Case_us.toml --set solver_options.withItemized=none
```

NY STAR is modeled (2026-10-17): give the home's `school_district` in `[basic_info]` (and in a
move to another NY home) and keep the budget's `property tax` line at the bill a listing shows
(the credit is a separate payment, not a lower bill). Basic credit, Enhanced from 65 while the
income two years earlier (AGI less IRA distributions) is under the limit. To see what it is worth:

```bash
owlcli compare otherFiles/Case_us.toml --set solver_options.withSTAR=none
```

For a decision near the Enhanced limit, `withSTAR = "optimize"` (or local search) lets the plan
keep its income under it; the loop does not try. `previousSTARIncomes` (in `units`) gives the
income of the two years before the plan; without it the two `previousMAGIs` are used.

Not modeled: NYC household and school-tax credits, part-year residency.

Differences under about 1% between residency variants can be loop noise rather than a real
difference, with either sign (see `PROGRESS.md`, NJ stakes). Keep the solver options identical
across variants, and for decisions run each variant with local search and with the exact LP:

```bash
# local search on both runs (--solver-opt applies to both; --set to the variant only)
owlcli compare otherFiles/Case_us.toml --set basic_info.locality=Yonkers \
    --solver-opt breakpointMethod=local-search
# exact LP on both runs
owlcli compare otherFiles/Case_us.toml --set basic_info.locality=Yonkers \
    --solver-opt withMedicare=None --solver-opt withSSTaxability=0.85
```

(`--solver-opt withSSTaxability=0.85` pins the fraction since upstream #174, merged 2026-10-08;
before, it stayed the text "0.85" and silently ran the loop.)

## 4. Work variants: the sweep (Phase 5 step 6)

Owl applies the SSA earnings test to every claim before FRA (upstream `6ea43a9`) and charges the
employee payroll tax on wages (upstream `3a2dfc33`), so work variants compare directly. Decide them
with `fork-notes/phase5/work_sweep.py`, not with `owlcli compare`: claiming ages need the
two-stage method of `fork-notes/plan-review-2026-10-22.md` §3.2 (decision R1). The script runs a
`withSSAges` search under the exact LP (ACA optimized when `slcsp_annual > 0`) and under the loop,
then scores the whole-year ages 62-70 and both picks at fixed ages by branch-and-bound at gap
1e-5, with the loop's `relTol` equal to the gap (`--decider bb`, the default since 2026-10-26; `--decider ls` for local search), which
decides. A direct `owlcli run` of the template's `withSSAges = "optimize"` with
`withMedicare = "optimize"` makes every candidate a branch-and-bound MIP under HiGHS.

Variants are a JSON file of `--set` overrides and HFP cell edits (format in the script's
docstring; a worked example: `fork-notes/phase5/work_sweep_chris+pat.json`). Keep the real one
in `otherFiles/`:

```json
{
  "set": ["solver_options.withSSAges=optimize"],
  "variants": [
    {"name": "both-stop-2026", "set": ["aca_settings.aca_start_year=2027"]},
    {"name": "B-part-time-2027-28",
     "set": ["aca_settings.aca_start_year=2027",
             "fixed_income.social_security_pia_amounts=[PIA_A, PIA_B_with_the_extra_years]"],
     "hfp": {"SpouseB": [{"years": [2027, 2028], "anticipated wages": 40000, "401k ctrb": 0}]}}
  ]
}
```

```bash
.venv/bin/python fork-notes/phase5/work_sweep.py otherFiles/Case_us.toml otherFiles/work_variants.json \
  --out-dir otherFiles/sweep --jobs 4 --json otherFiles/sweep/scores.json | tee otherFiles/sweep/report.txt
```

- One PIA per variant (decision D4: SSA's calculator in your account), set in the variant's `set`.
- Wages are the wages in AGI (#221); enter `months worked` in a spouse's last work year (it decides
  the grace year).
- The script writes each variant's workbook and case file to `--out-dir`, so any variant reruns
  with `owlcli run`.
- Read the *tol* column: a proved plan's distance to the model's optimum at its ages (the
  reported gap x the objective; about \$1.1/yr on chris+pat). A difference between variants
  larger than the two tolerances together is resolved; the report also lists ages whose scores
  are within their tolerances of the best one (a tie, not a pick). A plan branch-and-bound does
  not prove (a run not "Optimal", a time or node stop) is also scored by local search; then the
  *spread* column (local search's deepest dip between neighbouring ages) is the noise measure.
- A dip between proved plans is the model's own (on the dry run: Chris 67y0m, Pat 64y0m in the
  part-time variant). Under local search a dip can also be noise (the base variant's Pat 64y0m,
  `fork-notes/phase5/ws_bb_check.py`). `--json` keeps each scored plan's costs, to see what moves.
- `--report-from scores.json` reprints the report of a saved run without solving.
- Cost (dry run on chris+pat, 4 cores, `--jobs 4`): with branch-and-bound (2026-10-26) 29-51
  minutes per variant, 158 minutes for four, branch-and-bound solves of 84-632 s
  (`fork-notes/phase5/work_sweep_chris+pat_bb_2026-10-26_report.txt`); with local search
  (2026-10-25) 20-28 minutes per variant, 98 for four (`work_sweep_chris+pat_2026-10-25.txt`).
  HiGHS branch-and-bound can be much slower on another case: read the report's time-stop line.

The same script serves locality and rent/buy comparisons: a variant is any set of overrides.

## 4b. One stops and may claim SS; the other keeps working (a single comparison)

For a quick look at one variant, `owlcli compare` still works (claiming ages then come from the
case's own search, loop noise included).

Example: SpouseA stops at the end of 2026; SpouseB works through 2028 (full or part time) and the
employer plan covers both until then. Make a workbook with B's wages only:

```bash
uv run python fork-notes/phase0/gen_hfp_us.py otherFiles/HFP_us_oneworks.xlsx
# fill in: SpouseA wages for 2026 only; SpouseB wages 2026-2028 (part-time amounts if part time)
```

Then compare against the baseline:

```bash
owlcli compare otherFiles/Case_us.toml \
  --set household_financial_profile.HFP_file_name=HFP_us_oneworks.xlsx \
  --set aca_settings.aca_start_year=2029 \
  --set 'solver_options.withSSAges=["SpouseA"]' \
  --set "fixed_income.social_security_ages=[62.0, 67.0]"
```

What each setting does:

- `aca_start_year=2029`: family coverage through B's job ends with B's last year, so marketplace
  premiums start the year after. Owl keeps one start year for the household, which matches family
  coverage.
- `withSSAges=["SpouseA"]`: the optimizer chooses A's claiming age (62.0 is only the starting point)
  and keeps B's fixed. Since upstream `6ea43a9` (2026-10-24) Owl applies the SSA earnings test to
  every claim before FRA, earnings derived from B's wages, so `withSSAges="optimize"` may search B
  too (Phase 5 step 4: candidates carry the test). Enter `months worked` in B's last work year:
  it decides the grace year. (Before the test, the advice was to keep B at FRA while working.)
- Spousal benefits on B's record start only once both have claimed, as SSA requires. So A's spousal
  top-up, if any, waits for B's claim.

Two inputs to set per scenario by hand:

- **PIA.** `social_security_pia_amounts` is fixed; extra working years do not raise it in Owl. Use the
  PIA that matches the scenario. SSA statement estimates may assume continued work until claiming,
  so check what yours assumes, especially for the spouse who stops now.
- **Medicare past 65.** Owl charges each spouse Medicare from 65. If B worked past 65 with employer
  coverage and delayed Part B, Owl would overstate those premiums. Not an issue if B stops before 65.

## 5. Rent, buy with cash, or buy with a mortgage (Phases 2 and 2b)

Spending comes from a budget: `spending_profile = "budget"` builds the spending profile from the
`Budget` sheet of the HFP workbook, one line per item (`core` spending, `rent`, `property tax`,
`insurance`, `maintenance`, `car`, `travel`, `care`, `medical`, `charity`, `other`; `property tax`,
`medical` and `charity` are deductible when itemizing wins, `care` is not). `amount` is annual, in today's
dollars; `rate` is real growth above inflation in percent (0.5 is 0.5%); `year` and `end` are the
first and last calendar years (`end` 0 = through the plan end; negative counts back from it);
`survivor` is the percent kept after the first death (blank: the case's 60%, or 100 for the four
housing types). A line whose positive `end` is before its start adds nothing and draws a warning.
With a move, split the housing lines at the move year.

One HFP workbook per variant (`gen_hfp_us.py` writes empty `Debts` and `Fixed Assets` sheets and a
`Budget` sheet holding two essential `medical` lines, "gold over benchmark": 3,969 in 2027-2028
and 1,819 in 2029 for B alone, the cheapest gold plan's premium over the silver benchmark;
`fork-notes/aca-ny/README.md`, "Gold plans"; drop them for a silver plan), with the same
non-housing lines in each:

- **Rent** (`HFP_us_rent.xlsx`): `core` (and any car, travel, care lines; `gen_hfp_us.py` writes
  `core` with a placeholder amount: enter the real one here, `maxBequest` spends it) + one `rent` line.
- **Buy with cash** (`HFP_us_buy_cash.xlsx`): the same non-housing lines + owner's lines
  (`property tax`, `insurance`, `maintenance`); the price plus closing costs as a negative
  `big-ticket items` amount in the purchase year (one spouse's sheet; nominal $); the home in
  `Fixed Assets` (`residence`, `year` = the January after the purchase, `basis` = price, `value`,
  `rate`, `yod`, `commission`).
- **Buy with a mortgage** (`HFP_us_buy_mortgage.xlsx`): the same, with only the down payment and
  closing costs as the big-ticket item, and the loan in `Debts` (`mortgage`, `year`, `term`,
  `amount`, `rate`, and `property` = the residence's `name`).

Selling within the plan (e.g. before a move): set the residence's `yod` to the sale year, end
its budget lines the year before, start the next home's lines (or rent) in the sale year, and
name the residence in the loan's `property` column: the balance owed at the start of the sale year
is paid that year and the payments stop (upstream #173). With `property` blank the mortgage runs
to its term after the house is gone. A link Owl cannot honor (a name not in `Fixed Assets`, an
inactive home under an active loan, a sale before the loan starts) is an error.

How to read it: home equity cannot be spent in Owl, so compare with `maxBequest` and read
`final_bequest_today` (savings after heirs' tax, plus the house net of commission, minus any debt
left). Leave `netSpending` unset: each variant then spends its own budget (its first-year total is
the spending level), so the non-housing lines are the same in every variant. A `netSpending`
would scale each budget to that first-year total, by a different factor in each variant. `--set`
changes the variant only, so the objective goes in the base file: copy `otherFiles/Case_us.toml`
to `otherFiles/Case_us_housing.toml` and in the copy set

```toml
[household_financial_profile]
HFP_file_name = "HFP_us_rent.xlsx"

[optimization_parameters]
spending_profile = "budget"   # already the template's
objective = "maxBequest"

[solver_options]
breakpointMethod = "local-search"
# no netSpending: each variant's budget sets its own spending
```

then compare each buy variant with the rent base:

```bash
uv run python fork-notes/phase0/gen_hfp_us.py otherFiles/HFP_us_rent.xlsx
uv run python fork-notes/phase0/gen_hfp_us.py otherFiles/HFP_us_buy_cash.xlsx
uv run python fork-notes/phase0/gen_hfp_us.py otherFiles/HFP_us_buy_mortgage.xlsx
owlcli compare otherFiles/Case_us_housing.toml \
  --set household_financial_profile.HFP_file_name=HFP_us_buy_cash.xlsx
owlcli compare otherFiles/Case_us_housing.toml \
  --set household_financial_profile.HFP_file_name=HFP_us_buy_mortgage.xlsx
```

`housing_costs_today` in the output is the housing part of net spending. For the exact-LP
cross-check, override the base file's method on both runs:

```bash
owlcli compare otherFiles/Case_us_housing.toml \
  --set household_financial_profile.HFP_file_name=HFP_us_buy_mortgage.xlsx \
  --solver-opt breakpointMethod=loop --solver-opt withMedicare=None --solver-opt withSSTaxability=0.85
```

Loop noise rules from the residency section apply.

The **mortgage interest deduction** is modeled (Phase 3, `withItemized`, default `"loop"`): the
loan's interest, the property tax and the state income tax are itemized federally when that beats
the standard deduction (mostly 2026-2029, while the SALT cap is $40,400), and on NY's own schedule
every year it wins there. On the synthetic couple (exact LP, plans starting 2026-10-11, $600k home,
$480k at 6.5%; `fork-notes/model-review/phase3-review/housing_loop.py`), the deductions together
add $13.1k of bequest to buying with cash and $70.4k to the mortgage (statutory law; $10.2k and
$108.7k under the 2032 reversion). They narrow cash vs mortgage from $204k to $147k without
reversing it, and turn cash vs rent from rent ahead by $4.6k to cash ahead by $8.5k (0.6%: under the 1% below
which the Phase 1 rule calls a difference unresolved). To see what they are worth on our numbers:

```bash
owlcli compare otherFiles/Case_us_housing.toml \
  --set household_financial_profile.HFP_file_name=HFP_us_buy_mortgage.xlsx \
  --set solver_options.withItemized=none
```

compares the rent base (with deductions) to the mortgage variant without them; run the same
command without the last `--set` for the mortgage with them. The cash-vs-mortgage result also
turns on the mortgage rate against the assumed returns: with fixed rates it is a point estimate;
historical or stochastic ranges show the spread.

`maxSpending` answers another question with a budget: how large a version of this budget can be
afforded (every line scales, rent included). Use it for "can we afford this budget" (the basis
against the budget's first-year total), not to rank rent against buy.

## Federal law after 2031

The template uses statutory law (`obbba_expiration_year = 2066`: no reversion within the plan;
decision D1 in `fork-notes/phase3-plan.md`). Owl's own default reverts to pre-TCJA brackets and
standard deduction in 2032, which moves Roth conversions and withdrawals well before 2032. As a
sensitivity run:

```bash
owlcli compare otherFiles/Case_us.toml --set rates_selection.obbba_expiration_year=2032
```

Big-ticket items: signed, negative = expense, in the HFP and through the MCP assistant alike
(upstream 2026.10.10 fixed the MCP docstrings, which had described positive expenses;
`phase3-plan.md` §8).

## Healthcare cost sensitivity

Pre-65 marketplace premiums come from `aca_settings.slcsp_annual` (household benchmark Silver
premium, $k/yr, today's dollars). `withACA` does nothing while it is 0. Medicare, including IRMAA,
is priced endogenously by `withMedicare = "optimize"`.

The template carries 20.84: the 2026 Region 4 benchmark, the same for Yonkers, the rest of
Westchester and NYC (`fork-notes/aca-ny/README.md`, reading `dep26`). The 2027 benchmark is
21.4% higher (25.29 in 2027 dollars, so slightly high as a today's-dollar input), well above
inflation, because Fidelis drops its cheapest silver
plans; Owl grows the input with inflation only, so run that as a sensitivity:

```bash
owlcli compare otherFiles/Case_us.toml --set aca_settings.slcsp_annual=25.29
```
